# ai-prd-writer

**把"要不要做、做成什么样"的模糊讨论，压成 8–15 个选择题 + 一份能进评审会的 PRD。**

一个给 AI 编码助手用的技能（skill）。你说「写 PRD：<一句话场景>」，它会一次只问一个问题，问完给你一份 12 节、可直接过评审的 PRD 初稿。

关键区别：**问你是它的工作，不是它的失败。** 它不会替你编用户数据、业务指标、模型效果、数据集规模和项目排期——不知道就写 `【待确认：缺什么 / 卡住哪章 / 谁补】`。

## 30 秒安装

**Windows（PowerShell）**

```powershell
git clone https://github.com/xixi178249/ai-prd-writer.git
cd ai-prd-writer
.\install.ps1
```

> 若报「未对文件进行数字签名」，改用：
> `powershell -ExecutionPolicy Bypass -File .\install.ps1`

**macOS / Linux**

```bash
git clone https://github.com/xixi178249/ai-prd-writer.git
cd ai-prd-writer
./install.sh
```

脚本会自动找下面这些目录，找到哪个就装到哪个：

| 目录 | 对应工具 |
|---|---|
| `~/.dsh/skills/` | DeepSeek Harness 及兼容 harness |
| `~/.claude/skills/` | Claude Code |

手动装也只需要一步：把整个文件夹复制到上述任一 `skills/` 目录下，重启会话即生效。

## 装完怎么用

```
你：写 PRD：给 HR 做个筛简历的小助手，内部 30 人用

它：第 1 个问题——现在筛 100 份简历大概要多久？
    A 半天以上（每天简历量大，HR 明显是瓶颈）
    B 1–2 小时（能接受，但想省掉重复判断）
    C 没统计过，凭感觉慢
    D 你帮我定

你：A

它：第 2 个问题——AI 判断错了，后果是哪一档？
    A 自己能发现并纠正（容错高）
    B 会误导决策，需人工复核（默认推荐）
    C 会直接刷错人，必须拦住
    D 你帮我定
...
```

问满 8–15 题后，你会拿到《需求确认摘要》（已确认 / 代定 / 待确认 三段）。回「确认」才动笔，然后落盘成 `PRD_简历筛选助手_v0.1_20261121.md`。

三个快捷键：

| 你说 | 效果 |
|---|---|
| `你帮我定` | 它替你决定，句末标【假设】，进附录，可推翻 |
| `可以了，直接写` / `别问了` | 立刻停止追问，没答的全记【待确认】，直接出稿 |
| `不知道` | 不追第二次，记【待确认】，继续下一题 |

## 产出长什么样

12 节固定骨架，一节不少、一节不多：

```
1 背景与目标                2 用户故事与交互流程
3 效果定义                  3a Prompt Spec
3b Eval Spec                4 能力边界与不承诺清单
4a Agent 行为边界            5 数据需求与回流
6 成本预算                  7 兜底与风险
8 上线计划与灰度             9 后续迭代计划
+ 附录：假设清单 / 待确认清单 / 冲突记录 / 自检记录
```

节选一段真实颗粒度（来自 [`examples/01-ai-feature.md`](examples/01-ai-feature.md)）：

> **模型层｜抽取准确率**：口径＝在 200 条人工标注简历上，字段级完全匹配数 ÷ 总字段数；现状＝无基线；目标＝≥0.85。
> **产品层｜初筛耗时**：口径＝HR 从打开到决定的中位时长；现状＝约 4 分钟/份（HR 口头估算，未实测）；目标＝≤1.5 分钟。
> **因果假设**：准确率↑ → 字段免手填 → 耗时↓。**最不确定的一环**是 HR 是否真的信任字段而不复核原文。

完整可看的成品：
- [`examples/01-ai-feature.md`](examples/01-ai-feature.md) — AI 功能类（简历初筛）
- [`examples/02-non-ai-process.md`](examples/02-non-ai-process.md) — 非 AI 流程类（门店巡检），演示 `【不适用】` 怎么处理

> 两份样例的数字与公司名**全部虚构**，只用于展示格式与颗粒度。

## 它内部怎么工作

四个阶段，缺一个效果就打折：

| 阶段 | 做什么 | 结束条件 |
|---|---|---|
| **P0 INTAKE** | 你说清场景；若给了材料，先抽 fact card 再补问缺口 | 判出场景类型 + 至少 1 个业务动作 |
| **P1 GRILL** | 一轮一问，选择题带末位「你帮我定」 | 必问项覆盖 ≥90%，或你说"直接写" |
| **P2 CHECKPOINT** | 出《需求确认摘要》：已确认 / 代定 / 待确认 | 你回「确认」 |
| **P3 DRAFT** | 套模板出稿 + 跑 14 项自检 | 自检通过并落盘 |

每条事实都挂来源标记，这是它不瞎编的机制：

| 标记 | 含义 | 正文怎么写 |
|---|---|---|
| U | 你原话 | 直接写 |
| M | 材料原文 | 直接写；与你最新表述冲突时以你为准，冲突进附录 |
| A | 它代定（你说了"你帮我定"） | 句末 `【假设】` + 附录汇总 |
| P | 待确认 | `【待确认：缺什么 / 谁补】` |

没有 U/M/A 来源的内容，不许以陈述句进正文。

## 为什么不让 AI 直接写一篇

因为直接写的 PRD 有三个固定毛病，而且都很难自查出来：

1. **指标是编的**。"准确率 90% 以上"——分母是谁？谁数的？这类句子评审会上没人能验证，也没人能反驳。
2. **章节是缺的**。少了「什么情况下会失败」，开发阶段才发现；少了「及格线」，上线靠拍脑袋。
3. **排期是猜的**。模型不知道你的团队几个人、有没有别的项目插队。

本技能的解法很土：**把这三个坑变成必须填的格子，填不上就留白并写明谁补。** 留白的 PRD 比编圆的 PRD 有用。

## 想改它

- 想加追问项 → 改 `references/question-bank.md`
- 想调模板的必填力度 → 改 `references/template.md`
- 想加自检项 → 改 `references/checklist.md`，同时同步 `.github/workflows/lint.yml` 的行数上限
- **改了 `description` 一定要跑 `evals/trigger-cases.jsonl`**，那是唯一能发现"技能不再触发"的办法

仓库是唯一事实源。装好的副本只是部署物：改完重跑 `install.ps1` / `install.sh` 即可。

## 适用范围

**适合**：新产品立项、AI 功能定义、需求对齐会前准备、要向上汇报"这功能值不值得做"。

**不适合**：已有 PRD 只想润色、纯技术方案/架构设计、竞品分析报告、任务拆解排期。这些场景它也会触发，但它会先跟你说"这个不该我干"。
