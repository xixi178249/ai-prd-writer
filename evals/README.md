# 触发测试集

## 为什么需要这个

`SKILL.md` 的 `description` 是**唯一**决定这个技能会不会被调起的字段。改一个字，可能它再也不触发，而改的人不会收到任何报错。

所以每次改 `description`，跑一遍 `trigger-cases.jsonl` 的对照。

## 当前用例

| 类型 | 条数 | 编号 |
|---|---|---|
| 该触发 | 12 | 1–12 |
| 不该触发 | 8 | 13–20 |

不该触发的用例，覆盖的是最容易误触的方向：代码性能、数据查询、已有 PRD 润色、架构图、竞品分析、排期拆解、格式转换、缺陷排查。

## 怎么用

### 手工（最快）

拿着 20 句句子，逐句问自己（或问模型）："看到这句，你会调起 ai-prd-writer 吗？"

判分只看两件事：
- 该触发的 12 条，都触发了 → 通过
- 不该触发的 8 条，一条都没触发 → 通过

任一条不符 → `description` 要改。

### 自动（改 description 时用）

在任意支持工具调用的 agent 里，把 20 句逐条发进去，记录是否调用了 `skill` 工具，与 `should_trigger` 比对。

期望结果：20/20 一致。低于 18/20 就不要合并这次改动。

## 加用例的规则

1. **优先加"本该触发但没触发"的真实句子**——这比加反例更有价值。
2. 每条必须写 `why`，说明它归属哪一类场景，否则一年后没人知道为什么加这条。
3. 反例不要凑数。只加**相似但不同**的句子（例如"润色 PRD"而不是"写 PRD"）。
