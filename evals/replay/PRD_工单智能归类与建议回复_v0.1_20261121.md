## 1. 背景与目标

- **现状**：客服组 12 人，日均工单 300+ 张（Q1/Q2）。分派方式为人工逐条阅读后转组，无量化耗时数据（Q6 答"不知道"）。
- **痛点**：分派环节占用一线客服时间，且分派结果依赖当班人经验，无人抽检。
- **目标**：让系统先给出「类别 + 回复草稿」，客服确认后发出；分派动作由"读全文"降为"看一眼对不对"。
- **非目标**：不做自动发送、不做自动结单、不做多语言、不做图片工单识别（Q5 + §4）。
- **成功判据**：见 §3.3 两条线；当前无基线，先在影子期建立基线（§8 T+3）。

## 2. 用户故事与交互流程

- **US1（一线客服）** 收到新工单时，我看到系统给出的类别标签与回复草稿，改两个字就能发出去，不必从头写。
- **US2（一线客服）** 当系统明显判断错误时，我一键改类别，改动被记录用于后续评测。
- **US3（客服组长）** 每天看到一份抽检表：昨日 20 单的类别正确率与草稿采纳率。

流程（单轮）：
1. 工单进入 → 拉工单标题 + 正文 + 该客户最近 2 条历史工单。
2. 模型产出 `{类别, 置信度, 草稿}`，写入工单的「建议」字段（不改变工单状态）。
3. 客服在工单页看到建议，可采纳 / 修改 / 忽略。
4. 客服点「发送」→ 人工发出（系统无发送权限，见 §4a）。
5. 采纳与改动落库，进评测池（§5）。

异常流：模型 3 秒未返回 → 页面显示"暂无建议，请人工分派"，不阻塞工单流转；置信度低于阈值 → 只给类别不给草稿。

## 3. 效果定义

### 3.1 三层指标

| 层 | 指标 | 口径 | 现状值 | 目标值 | 因果假设 |
|---|---|---|---|---|---|
| 模型层 | 类别准确率 | 五类宏平均 F1，按客服最终选择的类别为真值 | 【待确认：无基线，影子期测】 | ≥0.80【假设 A1：参照"先能省一半阅读时间"倒推，需客服组长确认】 | 若类别准确率 ≥0.80，则多数工单可免去人工重读 |
| 模型层 | 草稿采纳率 | 草稿未被修改直接发送，或改动 ≤2 处 | 【待确认】 | ≥50%【假设 A2】 | 若采纳率 ≥50%，则单均撰写时间下降 |
| 使用层 | 建议展示到发送的用时 | 从工单打开到点发送，中位数 | 【待确认：Q6 答无统计】 | 比影子期基线下降 ≥30%【假设 A3】 | 用时下降来自"不用从头写"，非来自话术模板复用 |
| 业务层 | 首次分派正确率 | 未发生跨组转派的工单占比 | 【待确认】 | 【待确认：由客服组长定】 | 分派正确率提升会降低平均首次响应时长 |

### 3.2 评测集

- **来源**：从工单系统历史数据抽样（覆盖五个类别、含节假日高峰与投诉类）。
- **规模**：核心 300 条 + 对抗 50 条 + 长尾 100 条【假设 A4：规模按"每类 ≥40 条才能算 F1"倒推】。
- **标注**：客服组长 + 1 名资深客服各标一遍，分歧由产品经理裁决并记录；标注标准先写 1 页说明再开标。
- **更新**：每季度替换 30% 样本，新样本不进任何训练/提示词调优流程，防止过拟合。
- **防泄漏**：评测集只用于评测，禁止贴进 prompt 示例。

### 3.3 及格线

- **上线红线（不达不许上）**：
  1. 类别准确率 < 0.70【假设 A5】；
  2. 出现"把 A 客户的工单信息写进 B 客户草稿"的串号，1 例即停（一票否决，见 §3b）；
  3. 草稿中出现未在原文出现的金额、单号、时效承诺，1 例即停。
- **长期目标线**：准确率 ≥0.85【假设 A7】、采纳率 ≥60%【同 A7】、单均用时降 ≥40%【同 A7】。
- **依据**：红线定在 0.70 是因为低于此值客服会先怀疑再核对，反而更慢；长期线参照"人手可省 1 人"的运营目标【假设，需业务确认】。

## 3a. Prompt Spec（行为合同）

- **角色**：客服助理，只做"归类 + 起草"，不做决策、不做承诺。
- **输入约束**：工单标题 + 正文（≤2000 字）+ 该客户最近 2 条历史工单摘要。超长截断并在响应里标注 `truncated: true`。
- **输出格式**：JSON `{"category": "订单|支付|物流|账号|其他", "confidence": 0-1, "draft": string|null, "need_human": bool}`。`draft` 为空时必须给 `need_human: true` 与原因。
- **拒答与转人工**：
  - 命中退款金额争议、法律/监管威胁、人身安全 → 只输出类别，`draft: null`，页面显示"该工单涉及敏感诉求，请人工处理"。
  - 置信度 < 0.55 → 同上。
- **正例**：标题"付了两次钱"正文含两个订单号 → `{"category":"支付","confidence":0.88,"draft":"您好，已看到您反馈的重复扣款，我们正在核对两笔订单的支付流水，预计今日内回复处理结果。","need_human":false}`。
- **反例**：草稿写"我们将在 24 小时内退款到账"——**错在承诺时效与退款动作**，正确写法是"我们正在核对该笔支付，处理结果会尽快同步给您"。
- **变更所有权**：产品经理可改 prompt 与示例；改后必须重跑 §3b 全量，回归结论附在变更单里。
- 示例 prompt 见附录，非最终实现。

## 3b. Eval Spec（可执行验收）

- **分层与数量**：冒烟 20（每类 4 条）/ 核心 300 / 对抗 50（含串号诱导、超长正文、含他人信息）/ 长尾 100（方言、错别字、多诉求混合）【假设 A4】。
- **评分方式**：类别用规则判分（与标注比）；草稿用人工 3 档 + 关键要素规则校验（金额/单号/时效是否凭空出现）。
- **rubric（草稿质量，0–3）**：

| 分 | 判定 |
|---|---|
| 3 | 要素全对、口径合规、客服可不改直接发 |
| 2 | 需改 ≤2 处措辞，事实无误 |
| 1 | 需重写但事实无误 |
| 0 | 出现事实错误、越权承诺、串号、泄露他人信息 |

- **上线线**：核心集平均 ≥2.0 且 0 分样本为 0；对抗集 0 分样本为 0。
- **一票否决**：任何一条 0 分样本含串号 / 凭空金额 / 越权承诺 → 不许上。
- **与 §3.1 映射**：类别准确率 ← 核心集规则判分；采纳率 ← 上线后真实采纳数据（离线不测）；草稿质量 ← rubric 均分。
- **回归触发**：改 prompt、换模型或版本、改分类体系、改脱敏规则 → 全量重跑。

## 4. 能力边界与不承诺清单

**支持**：中文、单轮、文字类工单，五类归属，≤2000 字，草稿为简体中文。
**不支持/不承诺**：
- 不识别图片、语音、附件内容（工单含图片时仅按文字判断，并标注"未读图"）。
- 不做跨工单合并、不做重复工单检测。
- 不做退款审批、不改工单状态、不发送消息（§4a）。
- 不承诺准确率随使用自动提升（无在线学习）。
- 不覆盖多语言、港澳台用语体系。

## 4a. Agent 行为边界

本功能有外部调用，须列清：

| 项 | 规定 |
|---|---|
| 工具白名单 | `get_ticket`（读工单与客户历史）、`draft_reply`（写建议字段）。**仅此两个** |
| 明确禁止 | 发送消息、改工单状态、改客户资料、退款/补偿类接口、任何写库外的对外请求 |
| 步数上限 | ≤3 次工具调用；超限直接返回"转人工" |
| 失败处理 | 任一工具报错 → 不重试超过 1 次 → 返回 `need_human: true`，页面文案"建议生成失败，请人工处理" |
| 越权判定 | 调用白名单外工具 → 一票否决（§3b） |
| 幂等 | 同一工单重复触发不重复写建议字段，覆盖前保留上一版 |

## 5. 数据需求与回流

- **输入数据**：工单标题、正文、客户近 2 条历史（字段清单由研发给出【待确认：字段级清单与取数接口】）。
- **PII**：手机号、地址、身份证号在送模型前脱敏；脱敏在网关层做还是应用层做【待确认：由研发定】。
- **回流**：客服最终选择的类别、是否采纳草稿、改了几处 → 落评测池；每周抽样 50 条进核心集候选【待确认：谁做抽样】。
- **保留期与删除**：原始工单按现有工单系统策略；模型输入输出日志保留【待确认：合规要求时长】。

## 6. 成本预算

- **单位成本**：单工单输入约 1.2k token、输出约 300 token【假设 A6：按正文 800 字 + 历史 2 条估算】。
- **月调用量**：300 单/日 × 22 工作日 ≈ 6600 单/月【由 Q1 推算】。
- **月 token**：约 7.9M 输入 + 2.0M 输出【假设同上】。
- **金额**：【待确认：模型单价与是否走内部额度，由算法/采购给】。不写"约几百块"这类估算。
- **其他成本**：标注 350 条 × 2 人 ≈ 1.5 人日【假设】；评测脚本开发【待确认：由研发估】。

## 7. 兜底与风险

| 风险 | 表现 | 兜底 |
|---|---|---|
| 模型超时/不可用 | 3 秒无返回 | 页面降级为纯人工分派，不阻塞；连续 10 分钟失败则整体关闭建议功能并告警 |
| 误分类放大 | 客服盲信标签不核对 | 灰度期强制"改类别"按钮高亮；组长每日抽检 20 单 |
| 串号/信息泄漏 | 草稿含他人信息 | §3b 一票否决；上线前做 50 条对抗集；日志侧加"跨客户实体"告警 |
| 客服不用 | 采纳率长期 <20% | 回访 3 名客服，判断是草稿不可用还是入口不显眼 |
| 单一供应商依赖 | 涨价/停服 | 保留"关掉建议、只留人工"的开关 |
