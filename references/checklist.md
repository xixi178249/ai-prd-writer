# 交付前自检（14 项）

## A. 事实（任一不过 → 不许交付）

1. 正文每个数字都能回溯到用户原话或材料原文；回溯不到的一律是 `【待确认】`。
2. 没有"行业普遍 / 通常 / 一般来说 / 大家都"式的无源断言。
3. 专有名词（公司、产品、系统、人名）都有来源，或已标记待确认。

## B. 骨架

4. 12 节齐全（1 / 2 / 3 / 3a / 3b / 4 / 4a / 5 / 6 / 7 / 8 / 9），编号与标题未改。
5. 不适用的章写 `【不适用：<理由>】`，不是空白、不是删除。
6. 每节的「必填」项都有内容，或明确 `【待确认：缺什么 / 谁补】`。

## C. 效果与验收

7. §3.1 三层指标齐全，各有口径（分子、分母、算法）。
8. §3.1 写明因果假设（模型层 → 产品层 → 业务层），并指出最不确定的一环。
9. §3.3 有具体数字的红线，且给出定这个数的依据。
10. §3b 有 rubric 与一票否决项；Agent 场景评了轨迹。

## D. 边界与风险

11. §4 的"不支持列表"与"已知失败模式"是具体表现，不是"可能不稳定"。
12. §4a 有工具白名单、风险分级、任务预算上限（或写了【不适用】及理由）。

## E. 交付形态

13. 文末附：假设清单 / 待确认清单 / 冲突记录。
14. 无绝对日期：排期一律 `【待确认：需负责人给档期】`，或用 T+周 相对骨架并标"建议"。

---

## 判定

- **A 组**：必须 100%，有一条不过就整体不交付，先把该条降级成【待确认】。
- **B 组**：缺项必须为 0。
- **C / D 组**：缺项写进文末「自检记录」，逐条说明"为什么暂时补不上、谁补、什么时候补"。

## 交付话术（固定三段）

1. 文件路径 + 一句话说明这份 PRD 的核心判断；
2. `【待确认】` 清单（按"卡不卡开工"排序）；
3. 评审会上最该先吵的 3 个问题（我给，不是我替你决定，是给会议定议程）。
