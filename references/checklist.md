# 交付前自检（15 项）

## A. 事实（任一不过 → 不许交付）

1. 正文每个数字都能回溯到四种来源之一——U（用户原话）/ M（材料原文）/ A（AI 代定）/ P（待确认）；四种都回溯不到，才写 `【待确认：缺什么】`。
2. A 来源的数字，`【假设 A?】` 编号必须**紧贴数字**（同行、间隔 ≤20 字）；只在"依据"里笼统提一次算不通过，扫全文数字逐个验。
3. 没有"行业普遍 / 通常 / 一般来说 / 大家都"式的无源断言。
4. 专有名词（公司、产品、系统、人名）都有来源，或已标记待确认。

## B. 骨架

5. 12 节齐全（1 / 2 / 3 / 3a / 3b / 4 / 4a / 5 / 6 / 7 / 8 / 9），编号与标题未改。
6. 不适用的章写 `【不适用：<理由>】`，不是空白、不是删除。
7. 每节的「必填」项都有内容，或明确 `【待确认：缺什么 / 谁补】`。

## C. 效果与验收

8. §3.1 三层指标齐全，各有口径（分子、分母、算法）。
9. §3.1 写明因果假设（模型层 → 产品层 → 业务层），并指出最不确定的一环。
10. §3.3 有具体数字的红线，且给出定这个数的依据。
11. §3b 有 rubric 与一票否决项；Agent 场景评了轨迹。
12. 非 AI 场景：3 / 3a / 3b 都写了【不适用】+ 理由，**且都给了替代物**（3.1 换过程/使用/业务三层、3.2 换成验收用例集的位置说明、3a 换校验规则规格表、3b 换验收用例表 + 通过门槛）。

## D. 边界与风险

13. §4 的"不支持列表"与"已知失败模式"是具体表现，不是"可能不稳定"。
14. §4a 有工具白名单、风险分级、任务预算上限；若写【不适用】，**必须紧跟一句对外动作约束**（如"只允许调用 create_order，不允许改价/改已建单"），不许只写"不适用"了事。

## E. 交付形态

15. 文末附：假设清单 / 待确认清单 / 冲突记录；无绝对日期（排期一律 `【待确认：需负责人给档期】`，或用 T+周 相对骨架并标"建议"）。

---

## 判定

- **A 组**：必须 100%，有一条不过就整体不交付，先把该条降级成【待确认】。
- **B 组**：缺项必须为 0。
- **C / D 组**：缺项写进文末「自检记录」，逐条说明"为什么暂时补不上、谁补、什么时候补"。

## 交付话术（固定三段）

1. 文件路径 + 一句话说明这份 PRD 的核心判断；
2. `【待确认】` 清单（按"卡不卡开工"排序）；
3. 评审会上最该先吵的 3 个问题（我给，不是我替你决定，是给会议定议程）。
